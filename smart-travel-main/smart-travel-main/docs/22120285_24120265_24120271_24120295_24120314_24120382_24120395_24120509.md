## 2. Project Concept and Unique Selling Point (USP)

This project proposes a smart travel recommendation system that generates personalized suggestions for food and sightseeing based on user constraints (budget, distance, preferences, and physical accessibility).

**Unique Selling Points:**
- **Explainable AI and Computational Thinking:** The system moves beyond basic filtering by applying a weighted scoring algorithm. It explains why a location is recommended (for example: "Fits budget + 2 km away + wheelchair accessible"), demonstrating clear abstraction and algorithm design.
- **Microservices Architecture:** Unlike traditional monoliths, the project utilizes a scalable micro-architecture, leveraging the strengths of Java for robust business logic and Python for data processing.
- **Inclusive and Safe Design:** The platform is deeply focused on accessibility (barrier-free routing) and real-time safety, ensuring it serves all demographics, including vulnerable user groups.

## 3. Target Audience

The intended users encompass a diverse customer base, with a strong focus on accessibility and safety:
- **Budget Travelers and Students:** Seeking cost-efficient, nearby options for short city trips.
- **Backpackers and Independent Travelers:** Needing quick, practical local recommendations and real-time safety alerts.
- **Small Family Groups:** Looking for convenient recommendations, flat and accessible routes, with clear indicators of cost and safety.

## 4. Technology and System Architecture

The project transitions from a basic script to a robust micro-architecture model to ensure scalability:
- **Frontend (User Interface):** ReactJS and TailwindCSS for a dynamic and responsive end-user experience.
- **Core Backend (API and Business Logic):** Java (Spring Boot) acting as the central API gateway, handling authentication, user requests, and data hydration via DTOs.
- **Data and Recommendation Service:** A standalone Python (FastAPI) microservice dedicated to data preprocessing, API integration, and computing multi-criteria algorithms.
- **Database:** PostgreSQL with the PostGIS extension for high-performance spatial queries (exact distance and radius filtering based on latitude and longitude coordinates).
- **DevOps and Deployment:** Docker (`docker-compose`) for containerization and GitHub Actions for CI/CD pipelines.

## 5. Key Features (Structured by User Experience Flow)

**Phase 1: Onboarding and Personalization**
- Adaptive UI setup (high contrast, large font).
- Profile initialization (preferences, wheelchair requirement, allergies).

**Phase 2: Search and Recommendation**
- Multi-modal input (form, AI chatbot integration, voice control).
- Explainable recommendation output (Top K locations with transparent reasoning).
- Text-to-speech support for visual assistance.

**Phase 3: Routing and Real-world Interaction**
- Barrier-free routing mapping (prioritizing wide sidewalks and avoiding stairs).
- Contextual warnings (real-time weather or environmental alerts).

**Phase 4: In-trip Safety**
- Floating SOS button to simulate sending current GPS location and alerts.

**Phase 5: Post-trip Experience**
- Personal wishlist and crowdsourced reviews (for example, confirming accessibility).
- Shareable itinerary links and automatic profile update (feedback loop).

## 6. Data Resources

Moving away from static mock datasets, the system will utilize:
- **Live APIs and Crawling:** Gathering real place information (coordinates, live ratings, categories, price levels) via Google Places API or TripAdvisor data.
- **Spatial Data:** Using PostGIS to store and calculate real distances accurately based on spatial geometries rather than hardcoded estimations.

## 8. Group Teamwork Process and Commitments

Our teamwork process is based on clearly defined ownership, measurable progress tracking, and professional engineering practices:

- **Task Assignment:** Managed via Trello (Inbox, Backlog, In Progress, Review, Done). Each task has one main owner, one backup, and a strict definition of done (DoD).
- **Technical Workflow (Git Flow):** Members create feature branches and submit pull requests. Direct commits to the `main` branch are restricted. Every pull request requires peer review and QA verification.
- **Daily Discipline:** Each member commits to responding to communications within 24 hours, updating Trello status daily before 23:00, and reporting blockers promptly.
- **Weekly Cadence:** Weekly meetings are held to review completed tasks, unresolved risks, and next-week assignments.
